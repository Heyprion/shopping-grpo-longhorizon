# 初版 GRPO 无增益与 veRL LoRA 同步故障诊断报告

> 记录日期：2026-11-16 ｜ 原始实验目录：`outputs/analysis/sft-rl-diagnosis`

**结论：这轮 RL 首先存在一个已复现的实现故障，不能据此判断 GRPO 无效或 SFT 已经学满。**

保存的配置启用了 FSDP2、LoRA 和 `actor_rollout_ref.model.lora.merge=true`。当前安装的 veRL 0.8 在这条路径上，先临时合并 LoRA，取出共享存储的 `state_dict()`，随后恢复 actor 底座；真正发送参数的迭代器在恢复以后才被消费。因此发送给 rollout 的是恢复后的 SFT 底座，缺少正在训练的 LoRA 增量。双卡真实 FSDP2、真实 PEFT、直接调用安装包原方法的无优化器实验已经复现，修复后同一实验通过。

actor 的优化器确实更新了，所以不能说“完全没有训练”。问题是采样器没有跟随 actor，在线 GRPO 变成了以基本固定的 SFT 行为策略收集数据、actor 对这些数据进行带 PPO clipping 的更新；训练内验证也没有正确验证正在更新的 actor。最终导出的 adapter 有非零增量，独立测试结果可以略变，但这不代表训练期间形成了正常的采样—更新—再采样闭环。

**最重要的证据**

| 检查 | 结果 | 能说明什么 |
|---|---|---|
| 完整训练记录 | 连续完成 500 次有效更新，另有 209 次候选不足跳过 | 不是优化器从未执行 |
| 固定测试 200 题 | SFT 110/200，RL 109/200 | 净差 1 题；没有观察到实际增益 |
| 逐题测试比较 | 107 题共同成功，88 题共同失败；新增成功 2，丢失成功 3 | 不是整体能力大幅崩溃；McNemar 双侧精确 p=1 |
| 训练内验证 | 初始 SFT 42/50；最佳 RL 43/50；最佳步骤 150 | 表面增益仅 1 题，且受同步故障影响 |
| 原始双卡同步方法 | 发出的张量严格等于 BF16 底座，严格不等于 BF16(底座+已知 LoRA 增量) | 直接复现增量在同步时丢失 |
| 修复后的双卡同步方法 | 发出的张量严格等于 BF16(底座+已知增量)，actor 底座仍正确恢复 | 修复针对已复现机制有效 |
| 验证题小测 | 冻结 SFT 与第 150 步独立 adapter 都成功 5/12，且成功集合一致 | 在这组定向诊断题上没有新增能力证据 |

12 题小测选择的是原始验证的全部 8 道失败题，加前 4 道成功题，不能把 5/12 当作整体准确率。关键的任务 10441 是训练内最佳模型唯一新增成功题，冻结 SFT 在独立小测中也做对了；因此不能把该题的 0→1 稳定归因于 RL。执行实现、浮点运算及批处理等差异足以改变某些轨迹，temperature=0 不能消除所有这些差异。

测试集净差 1 题不能支持显著退化；同样也没有证据支持提升。这里的显著性检验只描述这 200 道题的成对差异，不是多次完整训练的方差估计。

**同步故障的代码机制**

安装包的 `verl/workers/engine/fsdp/transformer_impl.py`，`FSDPEngine.get_per_tensor_param`，原始逻辑等价于：

```python
with merged_lora_context(actor, backup_adapters=True):
    params = normalize_peft_param_name(actor.state_dict())
# 此处已恢复 actor 的底座；params 仍引用同一批存储。
return ((name, tensor.full_tensor().to(bfloat16)) for name, tensor in params.items())
```

`verl/utils/fsdp_utils.py` 的恢复逻辑使用 `param.data.copy_(backup)`，会改变这些共享引用实际读到的值。`normalize_peft_param_name` 只改键名和过滤 adapter 键，没有复制权重。PyTorch 官方也明确说明 `state_dict()` 是包含参数和缓冲区引用的浅拷贝：[PyTorch 2.11 Module.state_dict](https://docs.pytorch.org/docs/2.11/generated/torch.nn.Module.html#torch.nn.Module.state_dict)。

复现使用两张 GPU、FSDP2、一个 8×8 的小线性层和 PEFT rank=2，人工设置可解析的 LoRA 增量 +0.25，没有梯度计算、优化器或训练。两个 rank 都观察到：

```text
原实现：sent_equals_base=true,  sent_equals_expected_merged=false
修复后：sent_equals_base=false, sent_equals_expected_merged=true
两者：  actor_base_restored=true
```

这是对当前配置命中代码路径的直接复现，不是重新读取已经退出的历史 vLLM 进程显存。相关安装包源文件时间为本轮训练之前，源文件哈希、依赖版本、训练配置与日志哈希保存在 [provenance.json](../../outputs/analysis/sft-rl-diagnosis/provenance.json)。该证据足以把同步故障列为首要已确认原因；修复后能提升多少，仍需新的训练验证，不能从最小实验推算。

**SFT 为什么能涨，RL 为什么没有顺势继续涨**

SFT 对每个教师动作提供直接监督，能够学习协议、工具选择、查询写法和规格操作；它不依赖 rollout 权重同步。GRPO 则依赖当前策略产生有差异的结果，并将更新后的策略用于后续探索。同步故障使这条关键反馈链断开，不能把本轮的失败解释成“强化学习这个方法无用”。

本轮 SFT 的正式训练/验证为 889/99，选中第一 epoch 的检查点。assistant-token 验证 NLL 依次是 0.13135、0.13585、0.15308，后两 epoch 没有继续改善，最佳模型选择按规则生效。这不证明模型在全部购物技能上达到上限。当前可可靠量化的是本轮 SFT 与 RL 的同一新测试集比较；旧论文、旧清洗前 baseline 或旧 200 题分数不能直接混入。

**数据也有问题，但主要是检索难度覆盖，不是发现了数据泄漏。**

`prepare_data_splits.py verify` 已通过，SFT 正式归属、RL/验证/测试边界及文件一致性没有发现问题。本次没有重新清洗、打标签、改动正式名单或借用测试数据训练。

基于保存轨迹的首轮查询，使用当前冻结 BM25 索引离线重放检索，不运行新策略评测：

| 数据范围 | 题数 | 目标首轮排第 1 | 目标首轮排前 20 |
|---|---:|---:|---:|
| RL 训练中每题首次出现的轨迹 | 945 | 595/945=63.0% | 868/945=91.9% |
| 训练前 SFT 的 RL 验证轨迹 | 50 | 29/50=58.0% | 47/50=94.0% |
| 已有 SFT 固定测试轨迹 | 200 | 71/200=35.5% | 167/200=83.5% |

训练首次出现轨迹是训练过程中逐步出现的样本，不是全部在 step0 生成的冻结 SFT 样本；当前同步故障使其行为策略接近冻结 SFT，但不能把它视作严格受控的同分布对照。首位命中率差距是分布诊断证据，不足以量化它对最终成功率的全部因果贡献。

原始 train 来源的训练/验证比原始 eval 来源的测试更容易把目标直接排到第一。现有 simple/medium/hard 是结构复杂度标签，不能替代检索难度或模型实际解题难度。初始 SFT 在 RL 验证已是 84%，在测试只有 55%；这 29 个百分点差距在 RL 之前就存在，不能归因于 RL 后期过拟合。

RL 测试的 91 道失败题可以进一步分为：

| 保存轨迹中的目标商品状态 | 失败题数 |
|---|---:|
| 搜索结果曾展示目标，但没有打开它 | 54 |
| 搜索结果始终没有展示目标 | 26 |
| 打开过目标，随后规格、预算、改买或流程失败 | 11 |

在 SFT 中对应为 54/22/14。RL 仍缺少明显的检索、候选筛选和需求核验提升。RL 失败中 65 题 `r_option=0`，但大量轨迹根本没有打开正确候选，不能把这些全部诊断为“在正确商品上选错规格”。

**有效数据规模有限，但“全组同分”不是另一个实现错误。**

总计生成 3,412 组、13,648 条轨迹，实际优化 1,000 组、4,000 条轨迹，只涉及 487 道不同任务。1,899 组因奖励恒定被过滤，269 组 sampling invalid；另外存在可用组多于当次所需数量、候选不足后整次放弃等情况，所以不能将所有 accepted 标志直接当作实际已训练。实际优化轨迹的难度分布为 simple/medium/hard=340/1052/2608，即约 8.5%/26.3%/65.2%。

GRPO 组内奖励相同会得到零相对优势，动态过滤是合理机制；[DAPO §3.2](https://arxiv.org/html/2503.14476v2#S3.SS2) 对此有明确讨论。当前 Strict Reward 可以是部分分数，分析使用原始四因子乘积，没有把它简化成二元成功奖励。已生成轨迹中有 477 条获得部分分数。

每次优化只有 2 道任务、每题 4 条轨迹，跨任务梯度的方差仍可能较大。1e-6 学习率、新建 rank16 LoRA 和有限覆盖可能限制更新幅度，但本轮已经存在同步故障，尚不能把这些超参数中的任意一项确定为主因。此前配置 C 的采样实验只证明有效组吞吐改善，并未证明学习收益。

**熵：没有看到 RL 导致探索突然塌缩。**

训练日志的平均全词表熵，从前 50 步的约 0.113 变为后 200 步的约 0.103 nats；轨迹和动态选择在变化，且 rollout 受同步故障影响，不能据此单独判断策略熵演化。为避免上下文差异，另对 12 条固定 SFT 验证教师轨迹、每种难度 4 条、共 2,558 个 assistant labels 做冻结前向计算：

| 相同教师上下文，T=1 全词表熵 | SFT | RL adapter 单独加载 | RL 已有 merged |
|---|---:|---:|---:|
| 全部 assistant labels | 0.05480 | 0.05451 | 0.05443 |
| 查询参数 tokens | 0.49431 | 0.49245 | 0.49259 |
| 语法及其他 tokens | 0.01230 | 0.01199 | 0.01204 |

这组数据中语法及其他 tokens 占约 72.6%，所以全 token 平均熵很低，不能等同于没有语义探索。RL 实际训练组平均有 3.989/4 条不同动作序列。固定教师上下文上的 SFT→RL 平均 KL 约 7.74e-5 nats（单独 adapter）和 9.28e-5（merged），说明在该小样本上的策略变化很小；不能外推到所有失败状态，也不能将它当作 on-policy 成功率。

**BF16 合并还有数值损失，但不是首要故障的替代解释。**

第 150 步 adapter 与现有 merged 的逐张量检查，符合 BF16(底座+LoRA 增量)，未发现导出合并错误；但增量很小，全部权重中只有约 1.86% 的元素发生变化。合并舍入误差的 L2 范数与原 LoRA 增量 L2 范数之比约为 0.969。这个比例不能直接解释为“丢了 96.9% 的能力”，权重误差和行为能力不成线性关系。

单独加载 adapter 的固定前向及 12 题小测也没有显示明显增益，因此当前不能声称只改最终导出精度就能救回结果。FP32 计算后再转成同一 BF16 最终权重，也不能消除 BF16 最终表示的舍入。后续可以用独立 adapter 推理作数值对照；首要工作仍是保证实际 rollout 正确收到 actor 更新。

**已经完成的修复与验证**

新增 `src/shopping_grpo/training/grpo/weight_sync.py`，在临时合并上下文内对分片状态执行 `detach().clone()`，然后恢复 actor，继续按原键集合、原 BF16 同步方式传输。接入已有 `compat.install_torch_padding_fallback`，没有改写 site-packages、奖励、采样配比、训练预算、正式数据或历史结果。

新增回归测试覆盖共享存储恢复后快照保持增量、安装幂等及实际同步迭代器延后消费。针对权重同步、现有 kernel、检查点和融合输出的 11 项测试通过，Ruff 通过；修复前后真实双卡 FSDP2 最小复现通过。测试输出在 [tests.log](../../outputs/analysis/sft-rl-diagnosis/tests.log)，原始发送检查在 [sync_alias_probe.json](../../outputs/analysis/sft-rl-diagnosis/sync_alias_probe.json) 和 [sync_alias_probe_fixed.json](../../outputs/analysis/sft-rl-diagnosis/sync_alias_probe_fixed.json)。

快照会额外占用一份分片权重的临时显存。当前真实 2B 训练负载下的新增峰值及吞吐尚未实测，下一次执行前应做资源检查。没有启动新训练、重新合并生产模型或重跑固定 200 题测试；诊断服务已经关闭。

**要实现 SFT 提升后 RL 再提升，建议按这个顺序推进。**

1. 先验证修复后的真实模型 actor→rollout 同步：对若干层核对发送值包含 adapter 增量，并在固定状态比较 actor 与 rollout 的 log-prob。不要只确认更新接口被调用或同步函数返回成功。
2. 从原最佳 SFT 开始一轮新的短 RL 验证，先保留现有配方，隔离同步修复的效果。先看数十至约 100 次有效更新能否改善训练题及固定 50 题验证，记录逐题增减、真实参数差异和语义决策熵。旧 run 的训练内验证受故障影响，不应继续拿来证明旧超参数的优劣。
3. 只有闭环正确后再处理学习效率：依据训练池自身的实际成功概率、目标检索排名和组内差异构建诊断分层。覆盖“目标不排第一、需要改写查询、候选比较、跨规格预算判断”的任务，不能只按结构 hard 或有效组/分钟选题；不要从测试失败题反向构造训练数据。
4. 若修复后仍然移动很小，再通过训练/验证的小规模单因素实验比较学习率和有效任务 batch。可优先检查更多不同任务的梯度累积是否降低方差，再考察学习率；本次不直接断言更大学习率或更大 group 必定有效。
5. 对在训练池反复全失败的技能，纯结果 GRPO 不能从同分组中直接获得方向；必要时在独立的新 SFT 版本中补充教师成功示范，再进入 GRPO。不得把失败轨迹强行标成成功、改变奖励公式或用测试题补示范。
6. 以固定验证的可靠改善作为继续完整训练的依据。现有 50 题保留作对照；如需要额外验证覆盖，可在授权后使用预留验证用途题，不改成测试调参。完整训练和选模完成后才做一次固定测试报告。

这些是后续执行建议，本次没有自动更改配方或扩量。同步修复是必要条件，不是 RL 增益的保证。现有证据首先支持“这轮在线学习闭环有实现故障”，其次支持“检索与候选判断覆盖不足”；不支持“SFT 已经学满，因此 RL 天生没有用”。
