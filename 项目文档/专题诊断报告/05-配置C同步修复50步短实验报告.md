# 配置 C 同步修复 50 步短实验报告

> 记录日期：2026-11-16 ｜ 原始实验目录：`outputs/analysis/pilot50-results`

**结论：修复后的配置 C 正常完成训练，但前 50 次有效更新没有产生可测的验证成功率收益。下一步应做配方对照，而不是将本轮解释为 RL 无效，或直接原样跑满 500 步。**

| 检查 | 本轮证据 | 解释范围 |
|---|---|---|
| 固定验证集 | 42/50 → 42/50，新增成功 0、丢失成功 0 | 这 50 题的成功集合完全没有改善 |
| 验证动作序列 | 9/50 题发生变化，成功/失败仍未翻转 | 发生了行为差异，不能将所有差异归因于学习，也不能将它们算作新增能力 |
| 真实 adapter | 186 个语言层 LoRA B 张量的本地分片均有非零值 | 不是优化器未更新；冻结视觉分支的零值未混入计数 |
| 同步修复版本 | 运行登记的修复文件哈希与已通过真实闭环检查的文件相符 | 本轮使用修复后的同步路径；本轮未开启逐次权重哈希探针 |
| 梯度范数 | 0.088～0.232 | 未见梯度爆炸或全零 |
| PPO clip fraction | 平均约 0.0076%，最大约 0.075% | 没有大量更新被 PPO clipping 挡住的证据 |
| actor 熵 | 前 15 步平均 0.103，后 20 步 0.102 | 未见明显熵塌缩；不同批次的平均值不等于固定状态下的熵比较 |

检查点的三处语言层权重，LoRA 增量相对底座的 L2 比例约为 4.1e-5～5.5e-5，BF16 合并值中约 1.1%～1.5% 的元素变化。详见 [weight_change.json](../../outputs/analysis/pilot50-results/weight_change.json)。这支持更新幅度较保守，但没有通用阈值能仅凭权重相对范数断定学习率过低；参数距离不等于能力距离。

**有效训练覆盖比“跑了 50 步”听起来少。**

生成 364 个候选任务组、1,456 条轨迹；其中 212 组因组内奖励相同被过滤，27 组 sampling invalid。实际优化 100 个任务组、400 条轨迹，只覆盖 93 道不同题。另有 24 次候选不足而跳过的尝试，没有被误计为有效更新。

实际优化组的 simple/medium/hard 数量为 11/19/70；正式源清单没有变，动态奖励过滤后 hard 占比达到 70%。这是结构复杂度分布，不能据此断言这些任务在检索或模型能力上最有价值。

训练被使用轨迹的平均 Strict Reward，前 15 步约 0.567，后 20 步约 0.559；原始生成轨迹的成功率分别约 70.8%、71.0%。没有显示清晰的持续改善趋势，但各窗口采到的题不同，不能把它当作受控的训练准确率曲线或据此声称退化。

**这轮排除了哪些解释，又没有排除哪些。**

已有证据支持：训练确实执行、LoRA 确实改变、没有明显的梯度/熵/PPO 裁剪异常，固定验证却没有新增成功题。此前真实双卡探针已证明修复后的参数可以送达两个 vLLM 副本并用于后续采样。

没有证据支持：SFT 已经学满、bypass 导致训练崩溃、学习率一定太低，或某个数据配比必定最优。只有一组 50 步实验和 50 题验证，无法唯一归因于 batch、学习率、训练时长或分布覆盖；50 题的一个成功翻转就是 2 个百分点，也不能排除更小或尚未越过贪心决策边界的收益。

剩余 8 道验证失败题中，错误购买、循环和未完成轨迹仍是主要结果；一题是 reward_unverifiable。该轨迹无效不等于整道任务不可解，不能删除固定验证题或降低成功定义来制造提升。

**下一轮优先比较更大的有效任务 batch。**

这是待验证的假设：每次更新仅有两道任务，跨任务信号容易受个别长轨迹和任务内容影响；提高任务数有机会改善梯度估计和覆盖。它不是本轮已经证明的因果结论。

| 设置 | 已完成对照 | 建议下一轮 |
|---|---:|---:|
| 每次更新任务数 | 2 | 4 |
| 每题轨迹 group | 4 | 4 |
| 全局有效轨迹 batch | 8 | 16 |
| 每卡 micro batch | 4 | 4 |
| 双卡累积次数 | 1 | 2 |
| 学习率 | 1e-6 | 1e-6 |
| warmup | 15 步 | 15 步 |
| 有效更新次数 | 50 | 50 |

对应的核心覆盖为 `data.train_batch_size=4` 和 `actor_rollout_ref.actor.ppo_mini_batch_size=4`，micro4 保持。其余沿用修复后的配置 C，包括 seed42、group4、temperature1、bypass、Strict Reward 和正式名单。veRL 会按全局任务 batch、group 和每卡 micro 切分累积：[官方配置说明](https://verl.readthedocs.io/en/latest/examples/config.html)。

新对照必须从同一个最佳 SFT 起点重新开始，不能从当前 step50 接着训练后再与“从 SFT 训练 50 步”的结果直接横比。先比较训练前及第 50 步的固定验证，记录逐题增减，不能只比较汇总准确率。

batch4 的 50 次更新会使用 800 条实际优化轨迹，是本轮的两倍，因此同时比较轨迹用量和耗时。即使涨了，也不能仅凭这组结果把收益全部归因于 batch 降噪；它同时测试了每次更新更多任务及更大有效数据量是否实用。若需要严格区分两者，再安排匹配轨迹预算的对照，不应事后忽略成本差异。

如果 batch4 仍没有改善，再单独比较学习率 1e-6→3e-6，固定其他设置，观察概率比尾部、PPO 裁剪和验证翻转；当前不同时改变 batch、学习率、温度、难度配比或 bypass。不要用固定测试结果选择这些设置。

本次只分析已保存日志和模型参数，未启动训练、导出合并或新评测，也未改动正式配方。下一轮 batch4 是明确的实验建议，尚未执行。
