## 2. 数据来源及方案形成原因

完整来源是 `environments/ShopSimulator/shop_env/data/fine_items_eval_train_all.json.gz`，共 **23,421 个商品、23,421 条任务**，每个商品对应一条指令。原始记录包含：

- `asin`：商品标识；原始顺序对应当前任务 ID，不能通过删除或重排商品目录重新编号。
- `tag`：原始来源标签，只有 `train` 和 `eval`；对话中提到的“evil”对应 `eval`。
- `domain_zh` 等：9 个商品大类；`category` 是更细的类目路径。
- `instructions[0].instruction`：用户自然语言需求。
- `instructions[0].instruction_options`：标注的 gold 规格；`attributes` 是标注属性。
- `customization_options`：各规格轴、选项、价格、可用性；`pricing` 是商品价格或区间。

原始数据**没有用户需求数量或覆盖全量的难度标签**。已有指令 `attributes` 与商品属性复制关系很强，不能把它的长度直接当作用户提出的需求数量。旧 SFT 难度标签在清洗后只覆盖 953 条，而且来自旧教师轨迹，不能替代全量分层。

本次方案形成时作了以下明确决定：

1. 先用小样本验证两阶段筛选、错误样本和吞吐，结果只能是通过或不通过；不设人工复核队列。
2. 将奖励切换为论文的四因子乘积 Strict Reward，取消旧加权奖励、身份折扣及长度 shaping。详见 [奖励改动记录](reward-strict.md)。
3. 确认换奖励公式本身不会修复自然语言预算的漏解析，因此将模型提取的预算整理为规范字段，由清洗和奖励共用计算代码。
4. 用户明确要求全量清洗，包含旧训练、验证、测试任务；旧 200 题不再作为本轮清洗的隔离边界。
5. 清洗后重新规划用途边界：测试候选池来自**原始 `tag=eval`**，训练及阶段验证来自 `tag=train`，并处理跨来源重复指令。

旧测试 200 题中，只有 8 题的原始标签是 `eval`，其余 192 题是 `train`。因此新测试集不能直接沿用旧 200 题名单。此前的 SFT、RL 和评测结果保留其原始来源，不能改写成新划分下的结果。

## 3. 已完成的两阶段清洗

### 第一阶段：字段、格式及引用完整性

检查必要字段与类型、非空属性、有限非负价格、有序价格区间、规格选项可用性、gold 引用的存在性与唯一性，以及同一规格轴是否选了冲突值。原始字段缺失时不借助运行时默认值补齐。可选的副标题、persona 等不作为必填项。

### 第二阶段：语义一致性与静态可执行性

使用本地 **Qwen3.5-4B**，固定 revision `851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a`，关闭 thinking：

1. 提取器只看用户原始指令，输出 `requirements`、价格约束和不确定性。语义由小模型解释，不用正则提取规格。
2. 验证器核对提取需求与实际所选 gold 规格、商品证据；其他可选规格不能用作已购买规格的证据。
3. 代码核验引用证据、完整检查条目、跨轴符号尺码冲突、真实 variant 价格及预算算术，并检查 Strict Reward 静态 gold 终局。

只有全部必要需求满足、价格可确定且预算满足，并且能得到完整 `gold_purchase`、`reward_valid=true`、四项奖励均为 1，任务才通过。证据不足、语义无法确定、价格无法唯一解析、持久生成失败均自动不通过。

预算采用 `shopping-task-budget-v1`，区分 `parsed`、`not_mentioned`、`unresolved`，保存 CNY、价格作用范围、上下界、严格不等式及原文证据。“左右”沿用 +10% 上限容差；无法确定的单价、组件价格和组合价格不自行推算。`unresolved` 不得按无预算处理。

Strict Reward 始终为：

```text
r_type * r_att * r_option * r_price
```

它可以产生部分分数，不能把这个乘积误当成单一二元奖励。清洗要求 gold 达到完整成功，但这不改变 RL 中奖励的取值定义。

## 4. 确定的分层规则

使用 **9 个 `domain_zh` 大类 × `simple / medium / hard` 三档结构复杂度**。细分类目继续保留用于统计，不强求每个细类在小规模验证集或测试集中都有样本。

分层需要把清洗通过任务关联回固定的原始目录，补取 `tag`、`domain_zh` 和全部选项，校验 `task_id`、ASIN 和记录哈希。它们没有全部复制进 `tasks.jsonl`，不能假定导出文件已包含完整来源标签。

### 用户需求数的来源与口径

使用**上一轮清洗时小模型已经提取的 `requirements`**，不重新从文本用正则计算，也不使用原始商品属性列表代替。

首版口径固定为：统计 `hard=true` 且 `kind != category` 的条目。预算已单独存放，不计入这一项；软偏好不计入。这是模型提取的硬约束条目数，**不是经过严格语义去重的独立需求真值**。同义拆分、复合条目可能影响数值，所以所有阶段必须共用同一版本和计数口径。以后若引入原子化或语义去重，应另记分层版本，重新生成标签并记录影响，不能在各阶段临时改变计算方法。

### 首版结构复杂度评分

设硬约束条目数为 `n`；每个规格轴的可选值数为 `n_a`，可变轴数 `m = count(n_a > 1)`，最大单轴选项数为 `n_max`，无可变选择时按简单选择处理。选项统计基于清洗通过的原始记录。

| 子项 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 需求负担 | `n <= 3` | `4 <= n <= 6` | `n >= 7` |
| 规格选择负担 | `m <= 1` 且 `n_max <= 5` | `m = 1` 且 `6 <= n_max <= 19` | `m >= 2` 或 `n_max >= 20` |

两项相加：**0 分为 simple，1～2 分为 medium，3～4 分为 hard**。这是任务结构复杂度标签，不是模型实测成功率、教师轨迹长度或 token 数。首版阈值统一应用，不在每个品类或阶段内重新划分分位数。

正式标签已经生成，16,741 条分别为 **simple 2,532、medium 10,038、hard 4,171**。其中测试候选池 944 条为 101/560/283；除去跨来源重复封存后，训练来源 15,794 条为 2,431/9,477/3,886。预算边界余量、预算类型、检索目标排名和相似候选数保留为后续辅助诊断方向，当前不增加到主评分中。

## 6. 暂定训练数量和难度配比

以下是**初始参数，可以依据训练和验证结果调整**；调整参数不要求重做已固定的清洗，也不允许悄悄改变分层定义。

| 阶段 | simple | medium | hard | 唯一训练任务数 |
|---|---:|---:|---:|---:|
| **SFT** | **30%：240** | **50%：400** | **20%：160** | **800** |
| **RL** | **20%：200** | **50%：500** | **30%：300** | **1,000** |

比例按**唯一任务数**计算，不是 token 数、轨迹总采样次数或 GPU 时间占比。已经同时满足训练难度配额和商品大类的自然比例：大类配额用最大余数法取整，逐类相对自然期望误差小于 1 条；难度配额精确为上述数量。联合单元格采用 IPF 拟合两组边际，再做带库存上限的整数分配，尽量保留原品类与难度的关联，不能只改变难度而让整体品类分布随之偏移。所有首批训练、验证和测试均覆盖 9 大类。第一版混合打乱、均匀使用抽出的任务，不再叠加同一套难度采样权重，SFT 仍为单阶段训练。

SFT 的 800 训练、200 验证最终指各自通过质量检查的、唯一任务的完整示范轨迹。清洗任务文件不是可直接送入 SFT 的对话数据。教师采集失败时在同一候选池、同一层内按固定顺序补位，不通过重复同一任务凑数。RL 的 1,000 指唯一训练任务，group=4 等 rollout 设置仍按训练配方执行。

阶段验证及测试保持固定的自然分布，**不跟随训练配比反复重抽**。实际 simple/medium/hard 数量是：SFT 验证 **30/121/49**，RL 验证 **8/30/12**，测试 **21/119/60**。测试按 eval 候选池自身分布抽取，不套用 train 来源的比例。整数配额、联合分布及校验和已经写进 manifest；没有重复抽样凑数，50 题验证集的细层结果应结合样本数判断。

### 参考依据与后续调整

[DeReason](https://arxiv.org/abs/2603.11193) 为 SFT 侧重基础覆盖、RL 增加推理密集问题提供参考；[E2H Reasoner](https://arxiv.org/html/2506.06632v2) 提示过难任务可能导致稀疏奖励、需要保留可学习任务。这些结果主要来自推理基准，**没有证明本项目的 3:5:2 或 2:5:3 最优**。

后续结合固定验证集的分层成功率和训练诊断调整。例如：

- hard 任务频繁产生全零奖励组时，可把 RL 从 2:5:3 调为 2:6:2。
- simple 已稳定掌握、hard 也能产生有效奖励差异时，可尝试 1:5:4。

这些是待验证的调整方向，不是自动触发规则。当前 GRPO 组内做奖励减均值，组内实际奖励完全相同则优势为零；Strict Reward 有部分分数，不能只按成功 / 失败判断组内信号。[DAPO](https://arxiv.org/html/2503.14476) 对相同组奖励的问题有直接讨论。不能根据单轮小验证集的波动频繁调比，也不能使用测试集选择配比或训练数量。

每次调整训练样本数或配比，记录新的活跃任务名单、seed、数量、标签版本及校验和。固定验证和测试名单，保证不同训练设置可以比较。

## 7. 后续补题及续训时如何避免重用

登记表的 `selected` 表示已经被某批次占用，`available` 表示仍可抽取；`execution_status=not_started` 表示本次只固定了题目，不能把入选误报为已经训练。训练执行状态由实际训练产物记录。

补题先读取**本阶段训练池的剩余题目**，按所需数量和配比选出新批次，再更新登记表、剩余名单和 manifest。旧首批名单、验证集与测试集不变。每批保存独立文件，不覆盖先前批次，也不重复抽到已经入选的题。重复指令组保持同池、同批，不能拆开；首批优先使用独立指令任务。

```bash
# 查看再补 1,000 道 RL 新题的结果；不修改任何名单。
PYTHONPATH=src .venv/bin/python scripts/prepare_data_splits.py extend --stage rl --count 1000 --dry-run

# 用户要求补题时执行，产生 data/splits/rounds/rl_001.jsonl 和 .parquet。
PYTHONPATH=src .venv/bin/python scripts/prepare_data_splits.py extend --stage rl --count 1000

# 若本次明确调整难度比例，可指定 simple/medium/hard 权重。
PYTHONPATH=src .venv/bin/python scripts/prepare_data_splits.py extend --stage rl --count 1000 --ratios 10 50 40 --dry-run
```

SFT 补题使用 `--stage sft`，产生新任务名单，后续再采集对应示范。补题命令只分配题目，不启动训练或自动决定 checkpoint 恢复方式。数量或目标配额超出剩余库存时明确报错，不跨池、不复制任务。当前已验证补题预览及连续两批互不重用的行为，实际仓库还没有追加训练批次。

## 8. 其他会话启动训练时必须遵循的顺序
